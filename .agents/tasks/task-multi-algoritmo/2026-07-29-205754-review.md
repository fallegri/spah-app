# Multi-algorithm scheduling with execution history (v2)

The three critical issues from the v1 review — crossover gene ordering, repair capacity/type bypass, and config flag enforcement — have been addressed. Genes are now sorted by `(unidadIdx, sesionIdx)` before crossover. The `repairAndEvaluate` function builds an `espacioMap` and passes actual espacio objects for capacity/type/school validation. All three algorithms gate AIR and Sin Docente fallbacks on `config.permitirAIR` and `config.permitirSinDocente`, with practicas always allowed to use AIR. The `LIMIT 50` and dead-import removal are also in place.

**Watch for:** The resultados server page still fetches all executions without a limit (confirmed). The mutation operator in the genetic algorithm skips intermediate fallback paths that `generateIndividual` offers (confirmed). Greedy scoring still favors dense days over spreading (confirmed, design choice rather than a bug).

## High-level view

The genetic algorithm's structural correctness issues are resolved. The remaining concern is that `mutate` only tries the best case (docente + space) and worst case (AIR + Sin Docente), omitting intermediate options (docente + AIR, or sin-docente + physical space) that exist in `generateIndividual` and the other algorithms. Mutation can only improve a gene to full assignment or degrade it to AIR + Sin Docente — never finding the middle ground that the initial population and the greedy/iterative algorithms reach.

The results page server component at `resultados/page.tsx` fetches all executions unbounded (`orderBy desc` with no limit), while the API endpoint at `ejecuciones/route.ts` correctly applies `.limit(50)`. The two code paths serve similar data but only one was capped.

## Mutation operator missing intermediate fallbacks

In `generateIndividual`, there are four cascading attempts:
1. Docente + physical space
2. Sin Docente + physical space (gated on `config.permitirSinDocente`)
3. Docente + AIR (gated on `config.permitirAIR`)
4. AIR + Sin Docente (gated on both flags, or always for practicas)

The `mutate` function only implements steps 1 and 4:

```typescript
// Try docente + space
if (!unidad.esPractica && docentesCand.length > 0 && espaciosCand.length > 0) { ... }

// Fallback: AIR + Sin Docente
if (!mutated && (unidad.esPractica || (config.permitirAIR && config.permitirSinDocente))) { ... }
```

A gene that currently holds a "Docente + AIR" assignment will, when mutated, either find a full physical assignment (step 1 succeeds) or drop to AIR + Sin Docente (step 4). It can never find "Sin Docente + physical space" or "Docente + AIR" — the two intermediate states that represent partial improvements. This limits the genetic algorithm's ability to converge toward locally optimal solutions where docentes or spaces are scarce but not absent.

## Resultados page unbounded query

The server component fetches:

```typescript
const allExecs = await db
  .select({ ... })
  .from(ejecuciones)
  .orderBy(desc(ejecuciones.createdAt));
```

The API endpoint at `/api/scheduler/ejecuciones` applies `.limit(50)`, but the server component renders the same selector dropdown from an unbounded query. Over time this will serialize all historical executions into the page props.
