# Multi-algorithm scheduling with execution history

This change refactors a monolithic iterative scheduler into a three-strategy system (iterative, greedy-with-scoring, genetic) sharing extracted constraint helpers. A dispatcher in `engine.ts` routes to the selected algorithm based on `config.algoritmo`. The UI gains an algorithm selector with conditional genetic parameters, and the results page now lists all past executions rather than showing only the latest active one. The deactivation-on-run logic was removed so executions coexist independently in the database.

**Watch for:** The genetic algorithm's repair function skips capacity and space-type validation after crossover (confirmed), allowing invalid assignments to survive into the final solution. The `permitirAIR` and `permitirSinDocente` config toggles are displayed in the UI but never checked by any algorithm (confirmed). The crossover operator splices genes from individuals whose gene arrays may have different unit orderings due to shuffled processing, producing children with duplicated or missing sessions (likely).

## High-level view

The shared constraint layer in `shared.ts` extracts occupancy state management, validity checks, window computation, and work-unit construction into reusable functions. The key gap is that config flags `permitirAIR` and `permitirSinDocente` are never consulted — all algorithms unconditionally fall through to AIR/Sin Docente when no physical assignment succeeds.

The greedy algorithm enumerates every valid (day, window, docente, espacio) combination per session and picks the highest-scored option. The scoring function penalizes AIR and Sin Docente, rewards adjacency, and spreads daily load — though the adjacency bonus can override the load-spreading penalty, filling days to the 7-period hard cap before using a new day.

The genetic algorithm generates diverse initial solutions via randomized-greedy, then evolves them with tournament selection, single-point crossover, and per-gene mutation. The crossover and repair steps have structural problems: genes from different parents encode different unit orderings, so splicing at an arbitrary index produces children that reference sessions from mismatched contexts. The repair function re-validates overlap constraints but passes hardcoded `9999` capacity and `null` espacio for all genes, disabling capacity and type checks on physical assignments post-crossover.

The multi-execution model removes the deactivation query and adds an execution-selector dropdown driven by server-side searchParams. The new `/api/scheduler/ejecuciones` endpoint returns all executions without pagination, which will degrade as the table grows.

## Genetic crossover on mismatched gene orderings

Each individual is generated by processing work units in a *shuffled* order (`const shuffledIndices = shuffle(...)`). The resulting `genes` array therefore has a different positional mapping from index to (unidadIdx, sesionIdx) across individuals. When `crossover` performs a single-point splice at an arbitrary `point`, the two halves come from parents whose gene positions mean different things.

The `repairAndEvaluate` step catches *overlap* violations introduced by this, but it cannot recover *missing* sessions: if parent1's gene at index 5 covers session (unit 3, ses 0) and parent2's gene at index 5 covers session (unit 7, ses 1), the child ends up with one session duplicated and another absent entirely. The duplicated one will mostly be invalidated by repair, turning it into a conflict, but the absent one is simply lost — never scheduled, never reported as a conflict.

A fix: sort each individual's genes by `(unidadIdx, sesionIdx)` before crossover so positional correspondence is guaranteed. Alternatively, use a crossover operator that matches genes by identity (e.g., uniform crossover keyed on `unidadIdx|sesionIdx`).

## Repair function skips capacity and space-type checks

In `repairAndEvaluate`, every gene is validated with:

```typescript
isValid(state, gene.docenteId, gene.espacioId, studentKey, gene.dia, gene.slots,
        9999, materia.proyeccionInscritos || 0, materia.tipoAula, materia.escuela, null, gene.esAIR)
```

The `9999` capacity and `null` espacio parameters mean the HC-06 (capacity), HC-09 (type match), and HC-SCHOOL (school match) branches in `isValid` are all bypassed for non-AIR assignments. A gene that was valid in one parent's occupancy context will pass repair even if it references a room that's too small or the wrong type — because repair never looks at the actual room object.

The fix is to pass the real espacio (looked up from the unidad's candidate list or stored in the gene) so capacity and type are re-checked after crossover/mutation.

## Config flags `permitirAIR` and `permitirSinDocente` are dead code

No algorithm references these flags. All three unconditionally attempt AIR and Sin Docente fallbacks in their cascading attempts. A user unchecking "Usar AIR si no hay espacio" gets AIR assignments anyway.

Either wrap the fallback attempts (Attempt 2/3/4 in iterative, option types 2/3/4 in greedy, the corresponding blocks in genetico's `generateIndividual` and `mutate`) in conditionals checking these flags, or remove the toggles from the UI.

## Greedy scoring favors adjacency over day-spreading

The scoring penalizes high daily load progressively (`(currentLoad - 4) * 5`), which means a group at 7 periods (the hard-cap max) sees only -15. Combined with the +15 adjacency reward, a 7th period adjacent to existing ones still scores +0 net — so the algorithm will fill days to the 7-period max before spreading to a new day when adjacency is available. The hard constraint at 7 prevents overflow, but schedules will tend to be "dense days" rather than evenly distributed.

## Ejecuciones endpoint without pagination

The results page server component and the API endpoint both fetch all executions without a `LIMIT` clause. Scheduling tools accumulate runs quickly over multiple semesters. Add at minimum a `LIMIT 50` or a pagination parameter.
